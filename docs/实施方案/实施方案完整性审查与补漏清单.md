# 实施方案完整性审查与补漏清单

> 目的：从正式编码角度审查现有实施方案是否存在遗漏，并明确补充文档和开发约束。

---

## 1. 审查结论

现有方案已经覆盖产品主链路和核心业务模块，但在正式开发中仍可能因为横切能力不清晰而出现偏差。主要风险包括：

1. 前端组件各自请求后端，导致数据流混乱。
2. LLM tool calling 有契约，但缺少 Prompt 版本、模型评测和输出样例管理。
3. 用户输入、玩家操作、LLM 工具执行缺少统一权限与安全边界。
4. 错误、日志、任务失败、WebSocket 断线等运行问题缺少统一可观测方案。
5. 部署、环境变量、发布、备份和运维边界还不够明确。

因此需要新增以下补充方案：

- `数据流与前端状态管理方案.md`
- `安全权限与内容安全方案.md`
- `可观测性与错误处理方案.md`
- `Prompt工程与模型评测方案.md`
- `部署发布与运行维护方案.md`

---

## 3. 仍需在编码前最终确认的事项

1. 最终选定第一批美术资源包，并确认 license。
2. 确定第一版地图大小、建筑数量和室内地图清单。
3. 确定后端是否使用 RQ 还是 Celery 作为 MVP 队列。
4. 确定前端 UI 组件库使用 Ant Design 还是 shadcn/ui。
5. 确定 PostgreSQL embedding 维度，以实际模型输出为准。
6. 确定第一版部署目标仅本地 Docker，还是还需要云服务器部署。

---

## 4. 开发前强制检查清单

开始写核心代码前，必须满足：

1. `数据模型与接口契约V1.md` 已被后端 schema 和前端类型引用。
2. `ToolCalling工具契约V1.md` 已转成 ToolRegistry 初始工具定义。
3. `MVP开发任务拆分.md` 已转成 issue 或 sprint 任务。
4. `视觉资源与美术资产方案.md` 中的 MVP 资源已确认来源。
5. `.env.example` 已定义所有必需变量。
6. Docker Compose 可启动 PostgreSQL、Redis、后端、前端。

---

## 5. 反复审查原则

后续每新增一个核心能力，都要问四个问题：

1. 产品上用户是否看得见、感受得到？
2. 数据模型是否已经定义？
3. 前后端接口是否已经同步？
4. 失败和边界情况是否已有兜底？

如果任一问题答案是否，则不能直接进入开发。
