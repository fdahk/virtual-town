# 可观测性与错误处理方案

> 模块定位：统一错误模型、结构化日志、任务状态、LLM 调用记录、WebSocket 重连和问题定位能力。

---

## 1. 设计目标

AI 小镇包含仿真循环、WebSocket、LLM、数据库、Redis、Phaser 等多个环节。出错时必须能快速定位：

- 是前端渲染问题？
- 是 WebSocket 消息问题？
- 是后端仿真 tick 问题？
- 是 LLM 超时或格式错误？
- 是数据库/Redis 问题？

---

## 2. 统一错误模型

```json
{
  "code": "TARGET_NOT_REACHABLE",
  "message": "目标地点当前不可达。",
  "request_id": "req_001",
  "details": {
    "target_location_id": "loc_hobbs_cafe"
  }
}
```

错误分类：

| 前缀 | 类型 |
|------|------|
| `WORLD_` | 地图、碰撞、危险区 |
| `AGENT_` | Agent 状态或行为 |
| `MEMORY_` | 记忆写入/检索 |
| `LLM_` | 模型调用 |
| `TOOL_` | tool calling |
| `PLAYER_` | 玩家操作 |
| `WS_` | WebSocket |
| `DB_` | 数据库 |

---

## 3. 结构化日志字段

所有后端核心日志必须尽量包含：

```json
{
  "timestamp": "2026-04-30T11:00:00+08:00",
  "level": "INFO",
  "message": "agent decision completed",
  "request_id": "req_001",
  "simulation_id": "sim_001",
  "agent_id": "npc_xiaofang",
  "task_id": "task_001",
  "event_id": "evt_001"
}
```

---

## 4. LLM 调用记录

每次 LLM 调用记录：

- provider。
- model。
- prompt template id。
- latency_ms。
- success。
- retry_count。
- fallback_used。
- output_schema_valid。

禁止记录：

- API Key。
- 用户敏感隐私。
- 超长 prompt 全文。

---

## 5. 任务状态追踪

异步任务必须有状态：

```json
{
  "task_id": "task_001",
  "task_type": "agent_decision",
  "status": "running",
  "retry_count": 1,
  "last_error": null,
  "created_at": "2026-04-30T11:00:00+08:00",
  "updated_at": "2026-04-30T11:00:03+08:00"
}
```

状态枚举：

```text
pending / running / succeeded / failed / cancelled / timeout
```

---

## 6. WebSocket 断线处理

前端必须支持：

1. 自动重连。
2. 重连后请求 REST 快照。
3. 根据快照恢复 runtime store。
4. 继续接收 delta。

流程：

```text
WebSocket disconnected
  ↓
show reconnecting
  ↓
retry with backoff
  ↓
GET /api/simulations/{id}/state
  ↓
replace runtime state
  ↓
resume delta handling
```

---

## 7. 前端错误展示

用户可见错误要友好：

| 错误 | 展示 |
|------|------|
| 距离太远 | “离得太远了，靠近一点再互动。” |
| 目标不可达 | “这里暂时过不去。” |
| LLM 超时 | “对方思考了一会儿，但没有回应。” |
| WebSocket 断开 | “正在重新连接小镇...” |

---

## 8. 验收标准

1. API 错误统一格式。
2. LLM 调用有耗时和 fallback 记录。
3. 任务失败可查询。
4. WebSocket 断开后能恢复。
5. 前端不会直接展示后端堆栈。
