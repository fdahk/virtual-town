## 1. 项目目标与产品闭环

AI 小镇是一个浏览器内运行的 **2D 生活模拟小镇**：玩家可创建角色入场，与有人物档案、记忆、关系、自主决策的 NPC、动物互动；NPC 之间也会自发社交（请求-同意-拒绝）、自主吃饭/工作/休息，事件沉淀为记忆并影响后续行为。

核心闭环：

```
人物设定 → 自主计划 → 地图行动 → 玩家/NPC/动物交互 → 事件产生 → 记忆写入 → 后续行为变化
```

最小可演示规模：**6 个人类 NPC + 2 只狗 + 2 只猫 + 1 个玩家角色**，至少 1 个室外大地图 + 3 个室内场景，带 Portal 切换。

### 4.2 React 与 Phaser 的分工


| 角色             | 职责                                                              |
| -------------- | --------------------------------------------------------------- |
| React          | 业务面板（NPC/物品/对话/事件/观测）、路由、表单、TanStack Query 缓存                   |
| Phaser         | 地图与精灵渲染、摄像机、移动动画、点击/触摸命中、`BubbleManager`                        |
| ReliableSocket | 后端 → `worldStore` 仿真增量 + seq 检测 + 断线重连 + 快照恢复                   |
| EventBus       | `worldStore` 变更 → `TownScene` 移动/气泡；`TownScene` 点击 → React 选中面板 |


数据流：

```text
WS simulation.delta
  → worldStore.applyDelta()
  → eventBus.emit("agent:move" | "agent:state")
  → TownScene 播放动画 + BubbleManager.show(variant)

用户点击 NPC（Phaser）
  → eventBus.emit("agent:selected", id)
  → React 打开 AgentPanel / ChatPanel
  → 玩家发起对话 → POST /api/players/me/interaction-requests
  → ChatPanel 进入 requesting / accepted / soft_declined / hard_declined 四态
```

阶段 19 在 `BubbleManager` 与 `ChatPanel` 落地：

- 头顶富气泡 variant：`chat / work / eat / rest / sleep / thinking / awaiting / refused / interact / danger / blocked / drowning / speech`，持久态常驻、瞬时态自动淡出。
- `ChatPanel` 实现 4 阶段 UI（请求中 / 软拒台词 / 硬拒原因 / 已接受输入框）。
- NPC-NPC 自主对话广播 `dialogue.npc_to_npc_message` 时，旁观玩家可在地图上看到台词气泡 + 事件日志。

## 6. Agent 认知与决策管线

```text
每个 AI tick（默认 5 游戏分钟，世界 tick 默认 5Hz）：

1. perceive    视野内瓦片 / 物体 / 实体 / 新世界事件，过滤 unreachable 黑名单
2. retrieve    pgvector 相似度 + 时近性 + 重要度（embed 走 Redis 缓存 1h）
3. plan_ctx    层次计划：daily_plan → hourly_schedule → task_decomposition
4. decide      LLM tool calling（json_object）→ tool 校验 + 执行
                ├── 失败 / 未配置 → 规则版 RuleAgent 兜底
                └── 阶段 19：决策上下文带 _social_block（社交需求、上次社交时间、近邻熟人）
5. persist     更新 AgentState / AgentAction / Memory / Relationship
6. broadcast   simulation.delta + 领域事件（dialogue/world/interaction.*）
7. reflect     重要度累计触发 → 投递 daily_reflection 到 vt:low（不阻塞 tick）
```

行动结构（落库到 `agent_actions.action_type`）：

```text
move_to_location | move_to_entity | interact_with_object | avoid_danger
| face_entity | write_memory | search_memory
| react_to_pet | make_sound | update_emotion | wait
| request_interaction | socialize | end_chat
| work_at_location | have_meal | rest_at | browse_shop | observe_environment
```

完整工具矩阵以 `ToolCalling工具契约V1.md` 为准。

### 6.1 阶段 19：交互请求协议（请求-同意-拒绝）

状态机：

```text
                       request_interaction
                  ┌───────────────────────────┐
                  ▼                           │
          requester:AWAITING_RESPONSE         │
                  │                           │
                  │ InteractionEvaluator      │
                  ▼                           │
   ┌──────────────┼────────────────┐         │
   │              │                │         │
   ▼              ▼                ▼         │
 accept       soft_decline     hard_decline   │
   │            │  +npc_line     +reason     │
   │            │ target:        立即终止     │
   │            │ BUSY_REFUSING               │
   │            │ (短台词后回正常态)          │
   ▼            ▼                ▼          │
 进入对话       requester     requester     │
 (玩家走 /talk  收到 line     收到 reason    │
 NPC 走 npc_   后回 IDLE     后回 IDLE      │
 dialogue_loop  + 冷却         + Redis        │
 最多 10 轮)                   长冷却         │
                                              │
                            玩家或 NPC 取消 ──┘
```

数据：`agent_states.busy_until / interruptible / current_priority / last_social_at` + `interaction_requests` 全表生命周期。

评估三档（`InteractionEvaluator`）：


| 决策             | 触发条件（任一）                                                                                                     | 结果                  |
| -------------- | ------------------------------------------------------------------------------------------------------------ | ------------------- |
| `accept`       | 目标空闲、可打断、且关系熟悉度 ≥ 阈值 / 优先级足够                                                                                 | 双方进入对话              |
| `soft_decline` | 当前忙但不紧急 → LLM 生成短台词，规则兜底                                                                                     | 短期冷却 + UI 显示 NPC 台词 |
| `hard_decline` | 高优先级（≥ `INTERACTION_HIGH_PRIORITY_THRESHOLD`）/ 陌生人（< `INTERACTION_STRANGER_FAMILIARITY_THRESHOLD`）/ 已被同人连续硬拒 | 立即拒绝 + Redis 长冷却    |


WS 事件：

```text
interaction.request_pending  | requester / target / kind / reason
interaction.accepted         | request_id + 双方 id（玩家走 /talk，NPC 派发 dialogue_loop）
interaction.declined         | decline_kind ∈ {soft, hard} + npc_line / reason
interaction.cancelled        | 请求方主动取消 / 超时 expired
dialogue.npc_to_npc_message  | NPC-NPC 自主对话每条消息，地图旁观可见
```

详细契约见 `智能NPC与记忆模块实施方案.md` §9。

### 6.2 阶段 19+：自主社交闭环

光接通"请求-接受协议"还不够——若没有持续内驱动力，NPC 仍会一直按 schedule 走。
Engine 层的三个齿轮把"想找人 → 出手 → 落库"串成闭环：

1. **基础需求自然演化**（`SimulationEngine._evolve_basic_needs`）
  每 world tick 按 Δ 仿真分钟为每个 human NPC 累加 `social_need / hunger`、衰减 `energy`。
   `SLEEPING / EATING / RESTING / CHATTING` 状态有针对性的反向调整。
   **没有这一步，prompt 中的"社交需求"永远停在默认 0.3，阈值 0.55 永远达不到 → LLM 永不调 `socialize`。**
2. **NPC-NPC 自主邂逅扫描**（`SimulationEngine._scan_social_encounters`）
  每 `SOCIAL_ENCOUNTER_SCAN_MINUTES` 仿真分钟（默认 5）扫一次：找出 IDLE/WAITING 且
   `social_need ≥ 阈值` 的"急需社交者"，与同场景内 ≤ `SOCIAL_ENCOUNTER_DISTANCE`（默认 3）
   的另一空闲 NPC 配对，`asyncio.create_task` 调用 `InteractionService.create_request(kind="chat")`，
   走完整评估 / 广播 / 派发流程。
   触发后双方进入 `SOCIAL_ENCOUNTER_COOLDOWN_MINUTES`（默认 20 仿真分钟）冷却。
   **这是 LLM async 路径滞后场景下的"社交安全网"——即使没有 LLM，闲下来的 NPC 也会自然撞见。**
3. **工具记忆候选必落库**（`agent_decision._consume_memory_candidates`）
  `request_interaction` / `socialize` / `interact` 等工具在 `ToolResult.memory_candidates`
   里附了候选记忆。`decide_with_llm` 现在统一消费这些候选，用 `compute_importance`
   重打分后 `MemoryService.write` 写入 short_term。
   **这是修复"NPC 记忆里看不到对话"的核心一刀：之前候选完全没人写库。**

辅助调整：

- `socialize` 默认 `only_friends=False`，找不到熟人时降级到附近陌生人池（按距离）。
- 完成对话（NPC-NPC dialogue_loop / 玩家 talk）时，对应方 `social_need *= (1 - NEEDS_SOCIAL_DECAY_AFTER_CHAT)`，默认衰减 55%。
- `last_social_at` 在每次对话结束时统一更新，供 `_social_block` 给 LLM 提示"距离上次社交多久"。

完整配置项见 `智能NPC与记忆模块实施方案.md` §10.5。

1. **世界事件 → 个人记忆投影**（`app/domain/memory/event_projector.py`）
  `WORLD_EVENT_TOPIC` 上新增订阅者，把"NPC 看到 / 经历"的事件（公告 / 火灾 /
   暴风雨警告 / 互动 / 钓鱼 / 采摘 ...）按规则映射成短期记忆。
   Redis `SET NX EX` 跨进程去重，避免同事件同 actor 重复落库。
   配套修复 `NaturalEventContext` 的 `already_seen` 只能单 tick 去重的设计缺陷，
   改为长期 `recently_seen(key, minutes=...)` —— `world.sign_noticed` 之前每个
   world tick 都会刷屏（一秒数十条），现在每个 NPC × 每块告示牌 6 仿真小时一次。

验收信号见 §10.6 / §10.7。

### 6.3 阶段 20：分层记忆系统

> 详见专题：`[docs/实施方案/记忆系统重构方案.md](../实施方案/记忆系统重构方案.md)`。

**核心理念**：所有 NPC 经历的事件 / 对话都进记忆；不重要的不删，按主题
分层 summary 合并；重要的会被周期性回顾、强化、衍生新感悟。


| scope          | TTL     | 默认检索 | 用途                                         |
| -------------- | ------- | ---- | ------------------------------------------ |
| `working`      | 30 仿真分钟 | ✅    | 鸡毛蒜皮事件 / 对话每条消息（importance < 4）            |
| `short_term`   | 24 仿真小时 | ✅    | 业务主入口（importance ≥ 4）                      |
| `long_term`    | ∞       | ✅    | 重要事件、反思 thought、日结 / 合并 / 沉思 summary       |
| `archived`     | ∞       | ❌    | TTL 过期但还没合并；等 consolidation worker 处理      |
| `consolidated` | ∞       | ❌    | 已被某条 summary 收录（`summarized_into_id`），仅作证据 |


**两个新后台任务**（每仿真日各 1 次/NPC，错峰）：

- `**memory_consolidation`**（22:00 后入队）：扫过去 7 仿真天的 archived 记忆，
按 keywords[0]/subject 分桶；每桶 ≥3 条 → LLM 提炼 1 条 long_term summary；
原文 scope 改 `consolidated`，`summarized_into_id` 反指 summary。
- `**memory_rumination**`（10-14 点入队）：抽样 importance ≥ 7 的长期记忆，
让 LLM 重新感悟产出新 thought；同时给原记忆 `importance += 1` + 刷新
`last_accessed_at`，模拟"反复回忆 → 强化"。

**对话每条消息都进记忆**（`MEMORY_DIALOGUE_PER_MESSAGE=true`）：NPC-NPC 对话
循环里每条 `dialogue.npc_to_npc_message` 都为说话方/听话方各写一条 chat 记忆
（working scope）。30 分钟后过期归档，由 consolidation 合并成"今天和 X 聊
了什么"的主题摘要。

**访问强化**：`MemoryService.search` 命中后用独立 session 刷新被命中记忆的
`last_accessed_at`；`recency = max(exp(-Δ_created/168h), exp(-Δ_accessed/24h))`，
让被频繁回忆的旧记忆继续保持高分。

## 11. 仿真循环

### 11.1 时间步进


| 字段                                           | 默认    | 说明                                                                        |
| -------------------------------------------- | ----- | ------------------------------------------------------------------------- |
| `simulation_world_tick_hz`                   | 2     | 世界 tick 频率（Hz）：每真实秒约推进 `world_tick_hz×speed` 仿真分钟                         |
| `simulation_movement_substeps_per_game_tick` | 3     | 每仿真分钟内路径位移的子步数（同周期多次 WS 推送）；不改游戏钟，仅缓和移动观感                                 |
| `simulation_ai_tick_minutes`                 | 5     | AI 决策周期（游戏内分钟）：到点才调 LLM                                                   |
| `simulation_speed_default`                   | 1.0   | 倍速                                                                        |
| `simulation_autostart`                       | false | 冷启动是否把 `simulation.status` 收敛为 `running`（否则默认 `paused`）；与 DB 首行 seed 语义一致 |
| `simulation_reset_queue_on_start`            | true  | 冷启动是否清空 RQ 三条队列 + 收敛 PG `tasks` 的 pending/running，避免卷内残留 job 跨重启续跑        |


世界 tick 决定「多久走完一个仿真分钟」（决策 / 自然事件仍以该节拍运行）。同分钟内可走多格（`simulation_movement_substeps_per_game_tick`），在较低 `world_tick_hz` 下减轻位移卡顿（略增 WS delta 频率）。

### 11.2 主循环

```text
while simulation.running:
    world_step += 1
    world_time += tick_minutes
    1. 找出当前需要决策的 NPC（current_action 已结束 / 被外部事件打断 / 阶段 19 busy_until 到期）
    2. 入队 agent_decision（vt:high）—— 走 LLM；若未配置 → RuleAgent 同步走规则
    3. 推进未结束行动 → 更新 path / facing / 状态
    4. 写入 world_events / agent_actions / memories
    5. 触发反思批次 → 投递 daily_reflection 到 vt:low（不阻塞 tick）
    6. 广播 simulation.delta + 领域事件
    7. 等待下一 tick
```

### 11.3 性能保护（2026-05-01 落地）


| 优化                    | 落点                                                                                         | 收益                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| 不可达目标 5 分钟黑名单         | `world_tools.py` + `agent_decision._perceive()`                                            | 断"反复选同一不可达目标"循环（一次 trace 节省 ~75s）                                              |
| 决策链路并行化               | `agent_decision.decide_with_llm` 中 `asyncio.gather(retrieve, plan_ctx)`                    | 单次决策 -6s                                                                       |
| Embedding Redis 缓存 1h | `EmbeddingService.embed`                                                                   | 同文本 100% 命中，省 LLM 调用                                                           |
| 任务队列优先级分离             | `embedding`、`reflection` → vt:low；`agent_decision` → vt:high                               | 消除 embedding 积压阻塞决策（trace 一段 ~71s）                                             |
| 反思任务异步化               | `_maybe_reflect_batch` → `_enqueue_reflect_batch` 投递 vt:low                                | tick 不再因反思 LLM 卡 5-10s                                                         |
| 跨场景多跳路由               | `rule_agent._find_inter_scene_route` BFS                                                   | 解决"无路通往目标场景"长期 WAITING；rule_agent 与 LLM 共用 `agent:{id}:unreachable` 黑名单，避免反复尝试 |
| 主动追踪熟人                | `engine.start_pursuit` + `_refresh_pursuits` + `go_to_entity` 工具 + `_social_block` 暴露跨场景熟人 | NPC 想找谁就找谁，不再受"必须同场景"限制；目标移动时自动重新规划，距离 ≤2 即停下让 LLM 触发 `request_interaction`    |


详细复盘见 `docs/开发手册/debug/20260501-response-latency-optimization.md`。

### 11.4 决策吞吐扩容（2026-05-02 阶段 21+ 落地）

22 NPC 默认配置下，每 ~0.6 真实秒就会触发一次 `agent_decision` 入队（22 / `ai_tick_minutes`）。
SimpleWorker 单线程消费 LLM 任务（5-15s/次），把队列吞吐压到 ~0.2 jobs/s，导致绝大多数任务在
`deadline_seconds` 内被丢弃 —— 玩家观感即"只有少数 NPC 在动、其它 NPC 反复同样行为且没有记忆"。


| 优化                           | 落点                                                                                                                     | 收益                                                  |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| 自定义并发 worker                 | `app/domain/tasks/worker.py`：单进程 + N asyncio 并发槽 + Mini Scheduler 接管延迟重试                                               | 单 worker 吞吐 ~0.2 → ~3.2 jobs/s（concurrency=16）      |
| 决策锁去重                        | `engine._enqueue_decision_task`：入队前 SETNX `agent:{id}:decision_lock` (TTL ≈ deadline+60s)；handler 完成或 deadline 时主动 DEL | 同一 NPC 同时只有一份决策任务在跑，22 NPC 入队稳态自适应到 1.6-3.2/s 与吞吐对齐 |
| 启动错峰                         | `engine._load_state` 末尾按索引把 22 NPC 的初始 `last_decision_at` 分散到 `[0, ai_interval)` 仿真分钟内                                 | 第一波决策 burst 缓解，并发 worker 从启动即可流水线消费                 |
| DB 连接池扩容                     | `app/db/session.py`：`pool_size 5→20`、`max_overflow 10→20`                                                              | 匹配 16 路并发 × 1-2 session/任务，避免 worker 之间排队等连接        |
| `agent_decision` deadline 调长 | `agent_decision_deadline_seconds 60→90`                                                                                | 给并发吞吐留出余量，同时仍丢弃严重过期的决策                              |


新增配置项（`.env.example` / `Settings` 同步）：

```env
TASK_QUEUE_WORKER_CONCURRENCY=16    # 单 worker 容器内的 asyncio 并发槽位数（默认 16）
AGENT_DECISION_DEADLINE_SECONDS=90  # agent_decision 排队截止时间
```

扩容方法：水平方向继续用 `docker compose up --scale worker=N`；垂直方向直接调大
`TASK_QUEUE_WORKER_CONCURRENCY`。当前 16 槽位 × 2 session ≈ 32 ≤ 40 (pool_size+overflow)
仍有余量；若调到 ≥ 32 必须同步把 `app/db/session.py` 的 `pool_size+max_overflow` 一起扩到
≥ 该数值的 2 倍。继续向上还受 LLM provider RPM 上限与 PostgreSQL `max_connections` 约束。

详细复盘见 `docs/开发手册/debug/20260502-npc-decision-concurrency.md`。

## 12. 异步任务与短期记忆


| 队列           | 优先级 | 任务                                                                                              |
| ------------ | --- | ----------------------------------------------------------------------------------------------- |
| `vt:high`    | 5   | `agent_decision`（NPC 决策）                                                                        |
| `vt:default` | 4-6 | `dialogue_*` / `relationship_summary` / `daily_plan` / `hourly_schedule` / `task_decomposition` |
| `vt:low`     | 8-9 | `write_memory_embedding`（9） / `daily_reflection`（8） / `daily_summary`（8）                        |


- **消息层**：Redis + RQ。
- **状态 / 审计**：`tasks` + `task_status_log` 是权威源；Redis 结果 TTL 60s 即丢弃。
- **幂等键**：`{task_type}:{entity_id}:{simulation_step}`。
- **重试**：失败 + retryable + retry_count < max_retries → 自动回推 RQ + 指数退避。
- **部署**：`worker` 独立容器（`python -m app.domain.tasks.worker`），扩容直接 `docker compose up --scale worker=N`。
- **TTL Worker**：API 进程内的 asyncio 任务，按重要度把过期短期记忆升级长期或归档。

短期记忆 / 缓存 Redis Key：

```text
agent:{id}:short_memory          # 短期记忆 TTL 24h
agent:{id}:unreachable           # 不可达目标黑名单 TTL 5min
embed:{sha256[:32]}              # embedding 向量缓存 TTL 1h
dialogue:{id}:recent_messages    # 对话上下文窗口
world:{scene}:active_entities    # 场景在线实体
interaction:{requester}:{target}:cooldown  # 阶段 19：硬拒后冷却
```

Redis 不可用时自动降级到 Postgres，仿真继续。

## 13. 可观测性

观测平台与玩家页面**完全隔离**：独立 React 路由 `/observability`、独立 WS `/ws/observability`、独立 REST `/api/observability/`* 与 `/api/health/*`。

可观测维度：

- **Dashboard**：仿真 / WS 在线数 / LLM 平均耗时 / 错误率 / 任务分布
- **World Events**：世界事件流，按事件类型 / 实体 / 场景筛选
- **Obs Events**：跨模块观测事件流（trace_id / category / level）
- **Agent Runtime**：`agent_id` 视图：档案 + 状态 + Redis 热数据 + 最近事件 + 最近记忆
- **Traces**：`trace_id` 聚合观测事件、LLM、Tool、Task
- **LLM Calls / Tool Calls / Tasks / Errors**：全量审计表 + 聚合
- **Health**：`db / redis / llm` 实时探测

trace 边界（见 `可观测性与错误处理方案.md` §3.3）：

- 一次 **HTTP 请求** 自起一个 trace。
- 一次 **world tick** + 该帧延伸的异步任务（RQ）共享一个 trace。
- 默认脱敏：API Key / Authorization / password / `raw_prompt` 自动打码，超长字符串截断到 512。
