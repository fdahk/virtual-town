# AI 小镇正式开发架构指导

## 1. 文档拆分原则

`/Users/mac/virtual-town/docs/实施方案/React版AI小镇实施方案.md` 只作为整体架构总说明，不能承载所有模块细节。各核心模块必须单独新建方案文档，并写清楚以下内容：

1. 模块目标和边界。
2. 技术选型和选择理由。
3. 核心数据模型。
4. 后端接口与 WebSocket 事件。
5. 前端组件与状态设计。
6. LLM tool calling / function calling 契约。
7. 失败兜底、边界情况和性能策略。

模块文档之间必须保持数据模型和接口命名一致。任何接口或模型变更，都必须同步更新相关模块文档。

## 2. 世界与地图模块

世界与地图模块是本项目的底座，不只是地图渲染。它必须表达一个符合现实逻辑的 2D 生活世界。

必须设计并实现：

1. 室外大地图、建筑内部地图、建筑出入口、楼层/房间切换，整体参考《星露谷物语》式世界模型。
2. 建筑、自然环境、设施、家具、障碍物、危险区域、可交互物品。
3. 真实碰撞和环境后果，例如无护栏河流可进入并触发落水/溺水状态，有护栏时阻挡移动。
4. 动植物作为 Agent 实体参与世界运行。动物不是静态装饰，猫、狗等也要有感知、情绪、状态和反应。
5. 地图技术选型必须基于现代 Web 2D 游戏开发最佳实践评估，不能只因为原版项目使用 Tiled + Phaser 就直接沿用。

## 3. 仿真循环设计模块

必须设计合理的世界运行模型，保证虚拟世界高性能运行，不因 LLM 调用、NPC 数量增加或前端动画导致卡顿。

必须明确：

1. 前端渲染帧率、后端世界 tick、AI 决策 tick 三者的分离。
2. 后端作为权威世界状态，前端只负责渲染和用户输入。
3. NPC 行动执行和 LLM 决策异步解耦。
4. 活跃区域、空间索引、事件广播、增量状态同步策略。
5. 大量 NPC 和动物同时存在时的性能边界。

## 4. 智能 NPC 模块

每一个 NPC 实体包括人类、猫、狗等动物。动物与人类在系统建模上都属于 Agent，只是能力、行为工具和表达方式不同。

必须设计：

1. 初始模型层：年龄、外貌、职业、性格、长期目标、生活习惯、身体状态、认识的人、关系网络等固定初始数据。
2. 自主决策层：通过结构化 tool calling / function calling 输出可执行决策，而不是让 LLM 直接控制代码。
3. 成长与记忆层：区分感知上下文、短期记忆、工作记忆、长期记忆、情绪记忆、关系记忆、每日总结。
4. 记忆有效期、遗忘规则、重要度规则、向量召回、结构化召回和 Redis 短期上下文召回。
5. 初始世界需要预置约 6 个人类 NPC、2 只狗、2 只猫，并设计视觉样式、职业/习性、年龄、性格和互相关系。

## 5. 玩家模块

虚拟世界中除了自主 NPC，还必须存在真实玩家系统。玩家操作的角色也应该被建模为一个可被世界感知的实体。

必须设计：

1. 用户创建角色，输入性格、长相、背景等参数。
2. 玩家可移动、点击、探索、进入建筑、触发事件。
3. 玩家在可交互半径内点击人类 NPC 可打开对话框并输入文本。
4. 玩家点击动物可触发抚摸、靠近、喂食、惊吓等互动，动物需要产生真实反应。
5. 玩家与 NPC 的交互必须写入双方相关记忆，影响后续 NPC 行为。

## 6. 用户文本处理模块

用户输入不能直接拼进 prompt。必须经过语义处理、上下文召回和结构化响应。

必须实现：

1. Query 改写：结合用户操作角色的记忆、当前场景、对话对象，补全代词和模糊指代。
2. 意图识别：区分闲聊、询问、请求、命令、交易、挑衅、关怀等意图。
3. 上下文召回：从 Redis 短期记忆、PostgreSQL 结构化记忆、pgvector 语义记忆中组合上下文。
4. 结构化回复：LLM 输出不仅包含文本，还要包含情绪、动作、表情、关系变化、记忆写入建议和后续行动 tool calls。
5. 安全兜底：无关输入、恶意输入、超长输入、缺失上下文时必须有明确处理策略。

## 7. 工程化设计

正式开发必须具备可复现、可迁移、可协作的工程基础。

必须实现：

1. 数据库迁移工具，例如 Alembic。
2. Docker Compose，一键启动前端、后端、PostgreSQL、Redis。
3. 初始种子数据，包括地图、建筑、6 个人类 NPC、2 只狗、2 只猫、基础关系。
4. 一键启动脚本，例如 `scripts/dev.sh`。
5. `.env.example`，明确所有必需环境变量。
6. OpenAPI 接口文档、WebSocket 事件文档、数据模型文档、tool calling 契约文档。
7. 前后端类型对齐策略，优先从 OpenAPI 生成 TypeScript 类型，避免手写类型漂移。
