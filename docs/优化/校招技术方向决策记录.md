## 二、完整推理链（按 framing 演进切分）

本次讨论的真正价值不在最终结论，在于**每一轮都拒绝了一个先验框架并切换到更高层的框架**。下面按 framing 演进记录。

### 轮次 1：从"项目类型"开始
- **初始 framing**：在协同编辑器 / Web IDE / 监控 SDK 三个项目类型中选
- **当时给的推荐**：协同编辑器（方向 A）
- **被挑战**：是基于推理还是网上抄的？
- **暴露问题**：训练数据 anchoring——"协同编辑器"在中文社区被反复推，稀缺性其实在下降
- **修正**：加入"反调包侠"维度后重排序 → 监控 SDK（C）排第一

### 轮次 2：搜索空间问题
- **被挑战**：只在原来三个里选不对
- **暴露问题**：只重排不重新扩张搜索空间
- **修正**：列出完整分类学（协同/媒体/工具/基础设施/数据/AI/硬件/游戏/企业/特殊），补充被低估的方向（视频剪辑器、图片编辑器、WASM 数据分析、mini-Next.js）

### 轮次 3：framing 错了
- **被挑战**："项目类型"不是对的维度，应该按**技术专长**划分
- **暴露问题**：项目是 artifact，专长是 asset；专长比项目通用性强 10 倍（图形专长可投 Figma/AntV/ECharts/剪映/米哈游/数据 BU；"协同编辑器"项目只能投飞书/腾讯文档）
- **修正**：切换到"前端高壁垒通用专长" framing

### 轮次 4：高壁垒专长打分
按"通用性 × 壁垒 × 长尾 × 校招可达性 × 时间预算 × 面试杠杆"六轴打分：
- **Tier 1**：图形渲染、音视频
- **Tier 1.5**：工程化/编译（校招进不去，社招为主）
- **Tier 2**：性能/监控、跨端
- **结论**：图形或音视频二选一；性能作为前置入口

### 轮次 5：图形 vs 音视频
选**图形**，理由：
- 校招入口更多（可视化/设计工具/互动/大屏各家都有）
- 学习曲线建立在浏览器内（Canvas/WebGL/WebGPU 是浏览器原生）
- CS 数学基础可用（线代/几何是优势）
- 项目自包含性更强（音视频常依赖推流/服务端链路重）

路径：浏览器渲染原理与性能（1–4 月）→ 图形渲染（4–12 月）

### 轮次 6：AI 融合
- **被要求**：把 AI 融进去
- **首先泼冷水**：不接受套壳，否则违反之前立的"开源解决 80% 才有专长空间"原则
- **真融合发现**：WebGPU 既是图形 API 又是 compute API；端侧 AI 推理（onnxruntime-web WebGPU 后端 / WebLLM）正是基于 WebGPU compute → **这是真桥梁，不是 bolt-on**
- **结论**：WebGPU 从"进阶可选"提到"核心必修"

### 轮次 7：具体项目设计 v1
- 设计：**WebGPU 图像编辑器 + 端侧 AI 抠图**
- 技术骨架：统一 WebGPU pipeline，"一切皆 pass"，零 CPU 拷贝
- 硬 20%：推理与渲染的 GPU 调度

### 轮次 8：腾讯 + 全栈约束揭示
- **新信息**：目标是腾讯全栈工程师
- **诚实修正**：
  - 腾讯校招无独立"全栈" title，按前后端分轨；现实解读 = 投前端岗 + 全栈能力差异化
  - 原项目设计 95% 是前端，全栈维度残
- **添加真后端**：端云混合推理架构（Python FastAPI 推理服务 + Node.js 网关 + 异步队列 + 存储），不是 bolt-on，是真实产品（剪映/即梦）的真实工程决策

### 轮次 9：全栈定义澄清
- **用户回答**："前端为主 + 后端能写中型通用业务项目"
- **锁定 Path A**：前端 ≈ 65% / 后端 ≈ 35%；后端定位为中型通用业务（不是分布式高并发）

### 轮次 10：现有项目 Virtual Town 揭示
- **代码层证据**：后端 111 文件 / 前端 34 文件（3:1 后端倒挂）；0 处 WebGPU 调用；游戏部分 7 个文件，是 Phaser 业务层
- **诚实评估**：
  - ✅ AI Agent 系统：L3–L4（记忆架构、反思、工具契约、prompt 评测）
  - ✅ 后端基础设施：L3–L4（pgvector HNSW、RQ 任务队列、自研观测平台、可靠 WebSocket）
  - ❌ 图形渲染专长：L1–L2（Phaser 调包，不证明渲染深度）
  - ⚠️ 配比与"前端为主"倒挂
- **当时推荐 γ**：Virtual Town 当头号 + 另起小 WebGPU 项目补图形信号

### 轮次 11：用户 push back，修正为 γ'
- **被挑战**：项目方向/需求能容纳 WebGPU 和 agent，只是现在没写
- **承认混淆**：把"代码没写"和"方向不支持"混了，这是两件事
- **证据复核**：现有方案文档明确锁 Phaser，没规划 WebGPU → 走 WebGPU 是 v2 redirect，不是补全
- **但产品天然容纳**：scale 到 200 NPC、GPU perception、端侧小模型——三个集成点是产品驱动的，能过"为什么不用 Phaser"检验
- **最终修正**：γ → γ'，把 WebGPU 集成进 Virtual Town v2，单一连贯叙事

## 三、方法论沉淀（最有复用价值的部分）

这次讨论沉淀出的判断框架，比"最终选了什么"更值钱。

### 3.1 专长 vs 项目 vs artifact 区分

| | 含义 | 校招/简历价值 |
|---|---|---|
| 专长 (specialty) | 可迁移、跨公司、跨项目的能力（图形渲染 / 音视频 / 编译） | ★★★ asset 级 |
| 项目 (project) | 承载并证明专长的具体工程实体 | ★★ 证据 |
| artifact | 项目交付的产品产物 | ★ 演示用 |

- **错误**：把"我做了 X 项目"当卖点
- **正确**：把"我具备 Y 专长，证据是 X 项目 + Z 博客 + W 源码贡献"当卖点
- 简历叙事的反例与正例对照在 3.7 节

### 3.2 L1–L4 能力分层（关键框架）

| 等级 | 能力 | 校招/社招对应 |
|---|---|---|
| L1 会用 | 跑通官方 demo | 初级 |
| L2 会选 | 在 OSS 之间选型，讲清取舍 | 校招中高级 |
| L3 会改 | 给 OSS 写 patch、二次开发 | 社招中高级 |
| L4 会造 | OSS 不满足时自研 | 资深/专家 |

- **校招目标**：至少 L2，争取 L3
- **项目的真正价值**：把人从 L1/L2 顶到 L3/L4 的入口，而不是"做出一个产品"

### 3.3 高壁垒专长的判定（"80% 标准"）

| OSS 覆盖率 | 专家空间 | 例 |
|---|---|---|
| 100% | 不存在 | React/Vue 框架本身、CSS 框架、lodash、axios |
| 80% | 存在，剩 20% 是大厂业务需要 | 图形渲染、音视频、编译、性能监控 |

校招项目应押在 80% 类型方向上。100% 类型方向（再造一个生产可用框架）窗口已关，不要押。

### 3.4 真融合 vs 套壳的判定

对于"X 技术 + Y 技术"组合：
- **套壳**：Y 部分能被一句话 API 调用替代（"加个 AI 对话框"）
- **真融合**：X 和 Y 共享同一底层（如 WebGPU 同时是图形 + compute），架构上耦合而非堆叠
- **简历叙事检验**：能不能在 README 第一段回答"为什么不用现成的 OSS"

### 3.5 "为什么不用开源"是项目的命门

- 任何推荐项目，必须能用一段话回答：为什么不用 Konva/hls.js/Yjs/onnxruntime-web 现成的？
- 答不出 → 这就是劣质复刻，简历价值为零
- 答得出（性能瓶颈、特殊场景、产品策略） → 价值成立

### 3.6 三个筛"假项目推荐"的问题

任何人（包括我）给你推项目时，逼问：
1. **对应的 OSS / 大厂现成方案是什么？** 答不出 = 跑
2. **怎么和那个方案做技术对比？** 答"你自己写的就有价值" = 跑
3. **这个方向 2025–2026 大厂有自研投入 / 招聘需求吗？** 答不出 = 跑

### 3.7 项目叙事对错对照

| 错（"产品式"叙事） | 对（"能力式"叙事） |
|---|---|
| 我做了一个简版 Figma | 实现 WebGPU 矢量渲染引擎，对比 Fabric.js（Canvas 2D + retained mode），1 万图层场景 FPS 提升 6 倍，代价是 XX 内存占用 |
| 我写了 mini-Vite | 实现基于 esbuild 的 dev server，理解 Vite pre-bundling 设计动机，识别出 Vite 在 [具体场景] 的瓶颈 |
| 我做了监控 SDK | 对标 Sentry 实现监控 SDK，LCP 采集/上报通道选择了不同方案，理由是 XX，适用场景差异是 YY |
| 我做了 AI 图像编辑器 | WebGPU 渲染引擎，端侧跑分割模型，推理与渲染共用 GPU 资源调度，零拷贝合成 |

### 3.8 元方法论：epistemic 自检

- 当推荐看起来很"自然"时，问自己：是基于推理，还是基于训练数据/社区高频提及的 anchoring？
- 当用户 push back 时，**不要只在原 framing 内重排，要反思 framing 本身是否对**
- 信息池不会无限大，但每次新增重大约束（公司、时间、已有项目）都值得重新校准
- 区分"代码没写"和"方向不支持"——这是两个完全不同的判断

## 四、被推翻过的关键判断（避免回退）

记录这些是为了未来不再走回头路：

| 一度被推上来 | 推翻原因 |
|---|---|
| 协同编辑器（轮次 1） | 中文社区 anchoring，稀缺性下降 |
| 监控 SDK 作为主专长（轮次 4） | 壁垒不够高、长尾偏短，应作为入口而非主攻 |
| 音视频作为主攻方向（轮次 5） | 校招入口更少、学习曲线更陡（要啃编解码协议） |
| 工程化作为校招敲门砖（轮次 4） | 大厂工程化 team 社招为主，校招直接进难度大 |
| 自研 WebGPU 图像编辑器（独立项目）（轮次 7→11） | 与已有 Virtual Town 投资冲突，演变为 γ' |
| 两个独立项目 γ（轮次 10） | 缺乏单一连贯叙事，被合并为 γ' |
