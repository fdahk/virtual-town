## 一、本次升级修复的 Bug

### Bug 1：worker 进程内 `decide_with_llm` 偶发 `RuntimeError: simulation engine not started`

**严重程度**：P1（崩溃 + 任务失败）

**重现条件**：
- `TASK_QUEUE_MODE=async`，`agent_decision` 任务在 worker 进程消费。
- worker 进程独立运行（`python -m app.domain.tasks.worker`），其中**没有**启动 `SimulationEngine`（引擎只跑在 API 进程）。
- 当 LLM 返回 `emotion` 字段时，`decide_with_llm` 尝试把情绪同步回引擎内存：

```python
engine_agent = get_simulation_runtime().engine.get_agent(agent_id)
```

`get_simulation_runtime().engine` 在 worker 进程检测不到正在运行的引擎实例，抛 `RuntimeError("simulation engine not started")`，整个任务被标记为 failed，前一步的 LLM 决策结果（已经写入数据库的 `AgentAction`）随之被吞掉。

**复现日志（节选自 `terminals/1.txt`）**：

```
15:22:30 | ERROR | app.domain.tasks.handlers | agent_decision task failed
File ".../agent_decision.py", line 191, in decide_with_llm
    engine_agent = get_simulation_runtime().engine.get_agent(agent_id)
RuntimeError: simulation engine not started
```

**根因**：worker 进程不持有引擎，但代码假设引擎一定可用。情绪同步是"锦上添花"——下一次 world tick 主进程从数据库 reload 时，`AgentState.emotion` 仍会被读到，前端展示无差别。

**修复**：`backend/app/llm/agent_decision.py` 把同步逻辑包进 try/except，捕获 `RuntimeError` 走 debug log 而非异常传播：

```python
if plan.emotion:
    try:
        from app.services.simulation_runtime import get_simulation_runtime
        engine_agent = get_simulation_runtime().engine.get_agent(agent_id)
        if engine_agent is not None:
            engine_agent.emotion = plan.emotion
            engine_agent.dirty = True
    except RuntimeError:
        # worker 进程或测试环境中没有起仿真引擎；情绪通过下次 tick 重新加载
        logger.debug("engine not started; skip emotion sync for %s", agent_id)
    except Exception:
        logger.debug("emotion sync failed", exc_info=True)
```

**验证**：本地手测后台 worker 处理 `agent_decision` 任务，从 fail 变为 success；emotion 字段在下一轮 tick 通过数据库重新加载到引擎。

### Bug 2：`talk_to_entity` 与 `request_interaction` 工具语义重复

**严重程度**：P3（代码清晰度 / 一致性）

**根因**：阶段 19 引入完整的请求-评估-派发流程后，旧的 `talk_to_entity` 仍存在于注册表，且**只**做距离校验 + 写一条"想找 X 聊"的意图记忆（不触发任何对话），与新工具语义重叠。LLM 决策时可能误选旧工具，导致虽然"想找人聊"但社交协议未走通。

**修复**：
- 删除 `backend/app/llm/tools/dialogue_tools.py::TalkToEntityTool`，模块只保留 `FaceEntityTool`。
- 注册表通过 `from app.llm.tools import dialogue_tools` 自动减少一个工具。
- 同步更新：`tests/test_tool_registry.py` 显式断言 `assert "talk_to_entity" not in names`；`prompts/agent_decision/examples.json` 改用 `request_interaction`；`hierarchical.py` 决策提示工具目录替换；契约文档 `ToolCalling工具契约V1.md` 表格行删除并新增迁移说明（§5.1）。

**验证**：`pytest tests/test_tool_registry.py` 5 个用例全过；新断言生效。

## 二、新引入的运行时不变式

为了让分级拒绝策略 / 社交动机 / 忙碌状态机正确工作，本次升级在引擎层引入若干约束：

1. **`busy_until` 是引擎层的"占用"权威**：
   - `WORKING / EATING / RESTING` 状态下 NPC 必有 `busy_until > now_dt`，决策器跳过决策。
   - `busy_until` 到期后，引擎自动清理 `current_priority / interruptible` 并把 state 复位为 IDLE。
2. **`AWAITING_RESPONSE / BUSY_REFUSING` 是短暂状态**：
   - `AWAITING_RESPONSE` 30 秒真实时间后超时复位，`BUSY_REFUSING` 3 秒后复位（共享 `_chatting_since_real` 计数器）。
3. **NPC-NPC 对话**：
   - 由 `InteractionService._maybe_dispatch_npc_dialogue` 派发，仅当 accept + 双方均为 human 时触发。
   - `npc_dialogue_loop` 在 finally 块里强制调用 `engine.end_chatting`，避免循环异常退出后双方卡死在 CHATTING。
4. **冷却计数器**：
   - 同一对方连续 2 次硬拒后，Redis key `social:refusal:{requester}:{target}` 进入冷却（默认 30 仿真分钟≈360 真实秒）。
   - accept 时清零；冷却期内 `request_interaction` 直接返回 STATE_CONFLICT，避免反复打扰。
