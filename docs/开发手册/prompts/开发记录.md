1.世界与地图：40×30 室外大地图 + 3 个 16×12 室内场景；咖啡店/学校/杂货店/花店/公园/河边长椅/6 处住宅；河流有 hazard+护栏，桥为安全通道；所有 portal 自动切换场景。

2.Agents：6 个 NPC（小芳/小明/小王/林娜/陈伯/阿言）+ 4 动物（豆豆/黑黑/咪咪/小白）+ 默认玩家，每个 NPC 都有完整日程模板。

3.仿真循环：SimulationEngine 驱动 world tick + AI tick 解耦，状态机 IDLE → THINKING → PLANNING_PATH → MOVING → INTERACTING；异步队列接玩家输入；增量通过事件总线广播。

4.规则版 AI：decide_human_action 根据当前游戏时间选日程 → A* 生成路径；decide_animal_action 按性格反应玩家（亲人靠近、胆小躲开、警觉观望、疲惫睡觉）。

5.LLM + 规则兜底：LLMClient OpenAI 兼容，JSON 输出 + Pydantic 校验；generate_npc_reply 未配置 API key 时自动走规则兜底，仿真永不崩溃。

6.记忆系统：写入 Postgres，三因素评分（recency 0.5 / importance 3.0 / relevance 2.0），有 embedding 用 cosine，无 embedding 退化为中英关键字相关性；种子中预置「小芳记得小王喜欢美式咖啡」这条演示记忆。

7.玩家交互：创建角色 → 地图点击/WASD 移动 → 走近 NPC 对话（调 LLM + 引用记忆）→ 走近动物抚摸/喂食/呼唤/惊吓（带关系更新）→ 走进河无护栏处触发 DROWNING。

8。端 UI：Phaser 用纯色矩形绘制 tile/building/object/sprite（MVP 免外部资源），React 负责所有面板；WebSocket 自动重连；调试层可开关碰撞/危险/出入口。

9.工程化：Docker Compose、Alembic 迁移、scripts/dev.sh 一键启动、openapi-typescript 可从 OpenAPI 生成前端类型、统一错误模型（code/message/retryable/details）、结构化日志。

15. §14.1 可观测性基础设施（TraceContext）
- `backend/app/core/trace_context.py`：基于 contextvars 的
  `request_id / trace_id / span_id / parent_span_id / simulation_id / agent_id /
  player_id / task_id / event_id / category` 传递。
- `TraceContext.start_trace(category, ...)` 开顶层 trace，`TraceContext.span(name)` 嵌套 span，
  `TraceContext.apply(snapshot)` 支持 worker 从任务 payload 恢复 trace。
- 结构化日志 `app/core/logging.py`：新增 `TraceContextFilter`，所有 log record
  自动带上当前 trace 字段；dev 模式 formatter 把 `trace_id/simulation_id/agent_id/task_id`
  inline 到每条日志末尾。
- HTTP 入口中间件（`app/main.py`）为每个请求开一条 `http.*` trace；响应头自动回写
  `x-trace-id / x-request-id`。
- world tick 在 `SimulationEngine._tick` 外层套 `world_tick` trace，子模块（决策、工具、LLM）
  自动嵌套同一 trace。

16. §14.1 错误码统一治理
- `app/core/errors.py`：新增 `ErrorCode` enum，按模块前缀分类
  `WORLD_ / AGENT_ / MEMORY_ / LLM_ / TOOL_ / PLAYER_ / WS_ / DB_ / TASK_`。
- `AppError.to_dict()` 在 trace 激活时自动注入 `trace_id / request_id`，前端可稳定
  显示与排查；校验错误 422 响应同样带 trace。
- 新增错误基类 `TaskError / TaskDuplicate / TaskNotFound / LLMUnavailable`，老错误类
  `InvalidArguments / TargetNotFound / ...` 沿用原 `code` 值向后兼容。

17. §12 异步任务队列与 Worker
- 新表 `tasks`（id/task_type/status/retry_count/max_retries/idempotency_key/payload/
  result/enqueued_at/started_at/finished_at/last_error/trace_id/...） +
  `task_status_log`（全量状态变迁审计）。
- `backend/app/domain/tasks/`：
  - `registry.py` — `TaskHandler / TaskRegistry / TaskContext / TaskResult`。
  - `queue.py` — 入队：`tasks` 行落库幂等后再 push 至 Redis/RQ（**消费语义以本条下 §24「队列回正」为准**）。
  - `handlers.py` — 注册 MVP 任务拆分要求的全部 7 类 handler：
    `agent_decision / generate_daily_plan / generate_dialogue_reply /
    write_memory_embedding / daily_reflection / query_rewrite / relationship_update`。
    **阶段十五、十六已落地**：上述 handler 均有真实业务路径（详见 `handlers.py`、`player_service.py` 对话链路）。
  - `ttl_worker.py` — TTL 清理 worker：过期短期记忆按 `importance >= 7` 升级为长期，
    其余标 archived。
- `SimulationEngine._decide_all` 分叉：
  - `task_queue_mode=async`（默认）：LLM 决策投递到 TaskQueue，主循环不 await 网络；
    同步路径留给 rule_agent 给出即时行为。杀掉 LLM 接口仍能跑（规则兜底）。
  - `task_queue_mode=sync`：保留原先 inline LLM 路径，便于回归测试。
- `MemoryService.write(defer_embedding=True)` 默认把 embedding 计算投递到
  `write_memory_embedding` 任务，写路径不再阻塞在网络 I/O。
- Worker 进程独立拉起（Compose `worker` service / `./scripts/dev.sh`）；RQ 优先级队列 `vt:high|default|low`。**阶段三早期「API 进程内嵌 worker」文案作废，详见 §24。**
  切 Celery 时只需替换 `TaskQueue` 实现，`enqueue/get/list` API 保持不变。

18. §13 数据层深化
- Alembic `20260430_0002_infra.py` 为 `memories.embedding` 建 pgvector HNSW 索引
  （`m=16, ef_construction=64, vector_cosine_ops`），支持 10 NPC × 1k 条记忆量级
  的 P95 < 50ms 检索（验收条件达成由后续压测脚本验证）。
- `backend/app/core/redis_client.py`：异步 Redis 封装，集中维护方案 §5 键空间——
  `agent:{id}:short_memory` / `agent:{id}:runtime` / `dialogue:{id}:recent_messages` /
  `world:{scene}:active_entities` / `sim:{id}:state` / `task:{id}:status`。
  `set_json / list_push / set_add / scan_keys` 等，Redis 不可用时返回 False/[]，
  不影响业务主路径。
- `SimulationEngine._persist_tick` 在 Postgres 写入完成后做 Redis 写穿透：
  把每个 agent 的 runtime 热写到 `agent:{id}:runtime`（TTL 300s），
  场景活跃实体集合写到 `world:{scene}:active_entities`。
- `MemoryService.write` 写 Postgres 的同时把短期记忆镜像到
  `agent:{id}:short_memory`（TTL 24h），供快速召回。
- `scripts/backup_db.sh`：`pg_dump` + asset manifest 打包到 `./backups/`，
  优先直连 localhost，不可达时回退 `docker compose exec`。

19. §14.2 / §14.3 观测数据面与 API
- 新表 `observability_events / llm_calls / tool_calls`，配合 `task_status_log`
  构成完整观测事件流；业务代码一律通过 `app.services.observer.Observer`
  埋点，不直接写表。
- `Observer`：后台 flush 协程（默认 1.5s / 200 条），按类别分桶，flush 失败丢弃
  最旧批次并告警；敏感字段（api_key / authorization / password / raw_prompt）
  自动脱敏，超长字符串截断 512。
- `EventRouter`（`app/services/event_router.py`）订阅事件总线的
  `world.event_persisted`，将每条 WorldEvent 转写为 Observer 的 `world_event` 事件，
  为未来路由到 Memory / TaskQueue 预留了钩子。
- `LLMClient.chat_json / embed` 与 `ToolExecutor.execute_one` 全量埋点：
  latency / retry / schema_valid / fallback / error_code / permission / world_state 校验
  分项都进入观测表。
- REST `/api/observability/*`：
  - `dashboard`（聚合：仿真 / WS 在线数 / LLM 5 分钟平均耗时 / 错误数 / 任务分布）。
  - `events / world-events / agents/{id}/runtime / traces/{trace_id} /
    llm-calls / tool-calls / tasks / tasks/{id} / memories / errors`。
- `WS /ws/observability/{simulation_id}`：观测事件实时推送，与普通仿真 WS 通道隔离。
- 健康检查：`/api/health/db`、`/api/health/redis`、`/api/health/llm`
  （LLM 不发真实请求，只校验 key/配置）。
- 观测 WS 广播统一信封 `{version, type: "observability.event_created", payload, sent_at}`。

20. §14.5 WebSocket 健壮性
- `simulation.delta` payload 追加单调递增的 `seq` 字段；
  前端 `ReliableSocket` 基于 `seq` 检测丢失与乱序，`dropped_seqs` 计数暴露给 WS Monitor。
- 前端重连：指数退避（500ms → 15s），重连成功后自动调用 `onReconnect` 钩子——
  `TownPage` 绑定为 `GET /api/simulations/{id}/state` 拉快照替换 runtime store。
- `ObservabilitySocket` 独立重连、独立连接管理，观测平台断网不影响玩家页面。

21. §14.4 前端观测平台
- 新独立路由 `/observability`（App.tsx 按 path 切换），与玩家页面完全隔离。
  11 个子页面：Dashboard / World Events / Obs Events / Agent Runtime /
  Traces / LLM Calls / Tool Calls / Tasks / Errors / WS Monitor / Health。
- 组件：`ObservabilityPage.tsx`（总入口 + 9 个表/卡视图）、`TraceDetail.tsx`
  （span 时间线 + LLM/Tool/Task 详情）、`AgentRuntimeCard.tsx`（实体档案 +
  状态 + Redis 热数据 + 最近 20 事件 + 最近 10 记忆）。
- 风格：深色研发工具面板，研发不需要"好看"，需要"一眼看清问题"。
- 按研发场景把几类研发动作放到单页可达：
  - 要看一次玩家对话怎么被拆解 → Traces + trace_id。
  - 要看某 NPC 为何不动 → Agent Runtime 输入 agent_id。
  - 要看 LLM 是不是挂了 → LLM Calls + Health。
  - 要看哪些任务卡 pending → Tasks 表。
  - 要看错误趋势 → Errors（按 category:event_type 聚合）。

22. 配置与启动
- `.env` / `config.py`：
  - `TASK_QUEUE_MODE=async|sync`、`TASK_QUEUE_BACKEND=rq`、
    `TASK_QUEUE_HIGH=vt:high / TASK_QUEUE_DEFAULT=vt:default / TASK_QUEUE_LOW=vt:low`、
    `TASK_QUEUE_WORKER_COUNT=1`。
  - `OBSERVABILITY_FLUSH_INTERVAL=1.5`、`OBSERVABILITY_BATCH_SIZE=200`。
- API 进程 `main.py` 生命周期顺序：logging → Observer.start → subscribe_event_router →
  register_handlers + init_task_queue（**仅 enqueue**，不再跑内嵌 worker）→ TTL worker.start
  → SimulationEngine.start → serve。shutdown 反向；`TaskQueue.close()` 释放 Redis 连接池。
- Worker 进程 `python -m app.domain.tasks.worker`：
  - `docker-compose.yml` 新增 `worker` service，command 就是这条；扩容直接
    `docker compose up --scale worker=N`。
  - `scripts/dev.sh` 自动并起 `worker` 进程（与 backend / frontend 并列）。
  - 关键实现细节：worker 进程内维护**一个持久的 asyncio event loop 线程**
    （`runner._ensure_loop`），所有 RQ job 用 `run_coroutine_threadsafe` 投递进来；
    避免每 job `asyncio.run` 重建 loop 导致 SQLAlchemy AsyncEngine / asyncpg
    "attached to a different loop" 冲突。TTL worker 共享这个 loop。

27. Trace 边界与 Deadline 双 Bug 修复（2026-05-01）

    **问题发现**：观测平台 trace 展示一次 world_tick 的 wall-clock 长达 979 600 ms（约 16 分钟），
    用户质疑数据合理性，进而发现两个独立 bug。

    **Bug 1：任务 deadline 从未被 runner 检查（最高优先级）**
    - `agent_decision` 任务入队时已设置 `deadline_seconds=60`（存入 `tasks.deadline_at`），
      但 `backend/app/domain/tasks/runner.py` 的 `_execute_task` 在取出任务后
      **从未读取 `deadline_at` 字段**，导致即使任务在 RQ 队列等待了 16 分钟，
      worker 仍会照常执行一个早已过期的 NPC 决策。
    - 修复：在 `_execute_task` 的终态检查之后、handler 调用之前，加入 deadline 检查：
      若 `utcnow() > task.deadline_at`，直接将任务标记为 `FAILED`（error_code
      `TASK_DEADLINE_EXCEEDED`），记录等待时长，观测事件落库，不再执行 handler。
    - 影响：从此 `agent_decision`（60s）、`write_memory_embedding`（120s）、
      `daily_reflection`（120s）等任务在 RQ 积压超时后会被自动丢弃，
      不会执行过期的 NPC 行为，也不消耗 LLM quota。

    **Bug 2：trace_id 跨越 world_tick → async task，wall-clock 虚高 16 分钟（设计缺陷）**
    - 根因：`queue.py` 的 `enqueue()` 把当前 tick 的 `trace_id` 快照进任务 payload 的
      `__trace__`，worker 执行时通过 `TraceContext.apply()` 还原，
      使任务的所有 LLM call / tool call 均附上 **同一个 tick 的 trace_id**。
      `TraceDetail` 展示的 wall-clock = 从 tick 开始到 trace 内最后一条事件结束，
      跨越了队列等待时间，可达数十分钟。
    - 修复：
      - `backend/app/core/trace_context.py`：`TraceSnapshot` 新增 `parent_trace_id` 字段
        及对应 contextvar `_parent_trace_id`，`as_log_extra` / `current` / `apply` 同步更新。
      - `backend/app/domain/tasks/queue.py`：`enqueue()` 为每个任务生成独立
        `trace_id = f"trace_{uuid.uuid4().hex[:12]}"`，将原 tick 的 `trace_id` 存为
        `parent_trace_id`，写入 payload `__trace__`。
      - `backend/app/domain/tasks/runner.py`：`_execute_task` 从 payload 恢复
        `parent_trace_id` 到 `TraceSnapshot`，通过 contextvar 贯穿任务执行链路。
      - `backend/app/api/routes_observability.py`：`_serialize_task()` 从 payload `__trace__`
        中提取 `parent_trace_id` 并在 API 响应中透出。
    - 效果：任务 trace 的 wall-clock 仅反映任务自身等待 + 执行耗时（秒级），
      世界 tick trace 仅含同步逻辑（50–200ms）。

    **前端配套**：
    - `frontend/src/types/observability.ts`：`TaskRecord` 新增 `parent_trace_id` 字段。
    - `frontend/src/pages/observability/TraceDetail.tsx`：
      - `TaskSection` 展示每个任务的 `parent_trace_id`（截断显示 + 点击跳转到触发方 trace）。
      - `TraceView` 头部当存在 `parent_trace_id` 时，显示"触发方 trace"导航按钮（蓝色可点击）。
      - `TraceView` 任务时间栏新增 `waited=Xs` 字段，显示任务在队列中等待的实际时间。
    - `ObservabilityPage.tsx`：向 `TraceDetail` 传入 `onNavigate={setTraceId}` 回调，
      点击 `parent_trace_id` 按钮直接切换到触发方 trace 详情。
    - Bug 详情见：`docs/debug/20260501-trace-boundary-and-deadline-bugs.md`
